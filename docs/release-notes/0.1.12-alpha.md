## What changed in 0.1.12

Two correctness fixes from an execution-based review of 0.1.11, plus the documentation accounting
that review asked for.

**A rejected later FITS IMAGE header no longer truncates the file.** `FitsReader.Scan` caught a
`FitsFormatException` while walking later HDUs and simply stopped: a three-image file whose second
IMAGE header had `BSCALE=0`, or a PCOUNT/GCOUNT inconsistent with its payload, wrote only the first
frame, discarded the valid third frame, and exited 0 with SUCCESS. The same faults in the first HDU
were rejected. Image-header constraints now live in one place (`FitsImageConstraints`) used by both
the reader and `-check`, and a rejected header fails the file with the HDU named. A truncated second
data block still produces a labelled partial result.

Verified against independently written FITS bytes:

| Case | `-check` | Processing |
|---|---|---|
| BSCALE=0 in HDU 2 | exit 2, "HDU 2: BSCALE cannot be zero" | exit -1, FAILURE, 0 frames, input and HDU named |
| PCOUNT/GCOUNT mismatch | exit 2, constraint named | controlled failure, no SUCCESS |
| truncated data in HDU 2 | exit 2, byte count given | exit 1, PARTIAL FAILURE, 1 frame labelled incomplete |
| valid 3-HDU control | exit 0, "3 image HDU(s)" | exit 0, SUCCESS, **3** frames |

**Joined stacks keep the identity of the source that contributed.** A joined run named its single
unit after the first file, so a stack that selected only frames from the second capture wrote the
first capture's observer/telescope/instrument. Each frame now carries the file it was actually read
from through joining, retention and spilling, and the stacker's first-accepted rule sees the real
origin. Verified through the CLI with a flat capture and a planet-like capture: both input orders
select the planet frame and the header says `Observer-DISC`.

**Documentation now separates what the numbers mean.** The site previously said everything was
"measured against the original binaries" and labelled 926 as "tests passing". It now carries an
evidence table — managed tests, golden files, independent decodes, 27/27 parity, CI — states that only
the parity cases involve the original engine, and labels the approximately 94% figure as a weighted
estimate. The roadmap no longer claims "everything else is at or near exactness" and notes that the
23/30 tracking result is one Saturn fixture, not a general accuracy figure.

- Both fixes reproduced against the built Release CLI with fixtures written by the reviewer rather
  than by OPIPP's own writers.

## Known limits

- Median stacking retains at most 64 frames; disk-backed tiled median is not implemented.
- Mean/sum/median final stacking remains a Core API capability, not a CLI or GUI control.
- A Bayer-marked selection is stacked as ordinary samples (`Bayer=None` on the result).
- A valid image extension whose geometry differs from the first is still skipped under the documented
  same-shape rule.
- Floating-point FITS is converted to the integer model without scaling; 0.1-0.9 collapses to 0/1.
