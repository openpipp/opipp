# Memory model

## The problem

Every accepted frame used to stay resident until selection and output. Samples are 16-bit regardless
of source depth, so 10,000 frames at 1920x1080 is ~41 GB mono (~116 GB colour) before object overhead.
Selection does not help: it runs after the frames have accumulated.

## Design

- **`FrameStore`** (`src/Opipp.Core/Frames/FrameStore.cs`) — append-only scratch file holding
  transformed frames. Each record is a fixed metadata header (dimensions, channels, depth, Bayer
  pattern, source frame number, sample count) followed by raw little-endian samples. The file is
  opened with `FileOptions.DeleteOnClose`, so it cannot outlive the process even if disposal is
  skipped.
- **`RetainedFrame`** (`src/Opipp.Core/Frames/RetainedFrame.cs`) — a value-type handle that is either
  inline (the frame object itself) or stored (store + index). `Frame` materialises either
  representation, so the pipeline carries one type and call sites still read `.Frame`.
- **Budget** — `PipelineSettings.RetentionBudgetBytes`, default 512 MB of pixel data. Frames stay
  inline below it; the first frame that would cross it creates the store and **migrates the frames
  already accepted**, so a unit never has two homes for its frames. Small runs never touch the disk.
  The default can be moved for diagnostics with `OPIPP_RETENTION_BUDGET_MB` (megabytes), read when
  a settings object is created: unset, unparsable, zero, negative or overflowing values all leave
  512 MB. There is no CLI switch, so `-gui` transcripts and the engine protocol are unchanged.
- **Lifetime** — one store per `Run`, disposed before the report is returned.

## What stays the same

- Output bytes: `ForcedSpill_ProducesByteIdenticalOutput` runs 24 frames with a 1-byte budget
  (everything spilled) and compares SHA-256 of every output file against the in-memory run.
- Quality log: the source frame number is serialised with each stored frame, so `Pos/Source Frame`
  columns survive a spill.
- `-nr` / `-no_ram_buff` ordering: the reorder key is the source frame number, not the store index.

## Animation streaming

- **GIF animation** (`-anim_*`) also streams. The block order is defined over frame positions and the
  queue can re-read any frame (inline or spilled), so the sequence is generated by index — forward
  pass, holds, reverse pass — collapsing consecutive duplicates and dropping a closing frame that
  repeats the opening one, with O(1) frames held. A reverse pass re-reads frames, trading disk I/O
  for memory.
- **AVI animation** now streams like GIF. The count a container header needs is computed
  arithmetically (`CountAnimationFrames`) and the sequence is generated by frame index
  (`BuildAviAnimation`), so a reverse pass or a last-frame hold re-reads a frame instead of keeping
  a copy; the writer pulls one frame at a time. `-rgb` enumerates that one sequence once and
  splits each frame into the three sinks, so it is not restarted per channel. A four-frame
  `-avi -anim_fwd -anim_rev` AVI stays byte-identical to the engine's (parity case `anim`), and
  `tests/Opipp.Image.Tests/ContainerStreamingTests.cs` pins the SHA-256 of a five-frame animation
  so any byte change fails.

## Measured

`tools/Opipp.MemProbe` generates a synthetic 16-bit mono SER, runs the real `Opipp.Cli.exe` as a
child process with `OPIPP_RETENTION_BUDGET_MB` set, samples `PeakWorkingSet64` every 25 ms (with
`Process.Refresh()`, without which every read returns the start snapshot) and reports the peak.
Command:

```
dotnet run --project tools/Opipp.MemProbe -- --cli <Opipp.Cli.exe> \
    --frames <N> --width <W> --height <H> --budget-mb 32,4096
```

Host: Windows 11, .NET 10, framework-dependent Debug build of the CLI. Output: `-tif -q=10`
(10 TIFFs from every run), so the working set is dominated by retention, not output.

| Capture | Pixel data | Budget | Peak working set | Elapsed |
|---|---:|---:|---:|---:|
| 400 × 800×600 | 366 MB | 32 MB | **102 MB** | 6.2 s |
| 400 × 800×600 | 366 MB | 4096 MB | **597 MB** | 6.3 s |
| 1200 × 800×600 | 1099 MB | 32 MB | **93 MB** | 15.0 s |
| 1200 × 800×600 | 1099 MB | 64 MB | **146 MB** | 16.7 s |

Reading the table: at a 32 MB budget the peak is the same within noise for a capture three times
larger (102 MB vs 93 MB), and it scales with the budget rather than the capture (32 → 93 MB,
64 → 146 MB). Unbounded retention on the 366 MB capture peaks at 597 MB, i.e. the capture plus the
runtime.

Caveats: the peak includes the .NET runtime and transient transform buffers, so it is not the budget
plus zero; the figures are from a Debug build on this host and will differ elsewhere; and a budget of
4096 MB does not mean 4 GB was used — it means nothing spilled, which is the control case.

## Notes and remaining limits

- `GifWriter.Write` writes one image block at a time and builds a colour palette from a sampled pass
  without retaining frames; byte-identical to the buffered encoder for mono, colour, single-frame and
  animated output.
- The budget is not a CLI switch: `OPIPP_RETENTION_BUDGET_MB` is a diagnostic environment override,
  kept off the command line so `-gui` transcripts stay engine-identical.
- The budget bounds retained pixel data, not total process memory — the runtime, transform buffers,
  the reader and the stacker accumulator sit on top, as the measured table shows.
- `FrameStacker` accumulates a running sum rather than frames, so it is already bounded.
